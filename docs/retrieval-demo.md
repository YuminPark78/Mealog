# Local retrieval demo data

The fixture is based on the existing high-level dish **Guzman Bowl** and its
55 g carbohydrate amount. All fixture meals and glucose curves are synthetic.
No real Dexcom samples are copied, changed or generated by the seed script.

## Open the demo

1. Open `http://localhost:3000/account` in a private browser window so your normal
   account can remain signed in elsewhere.
2. Sign in as `retrieval-demo@example.com`. The generated password is in
   `private-data/retrieval-demo.json` at the repository root. This file is ignored
   by Git and readable only by its owner.
3. Open the reference **Guzman Bowl with Chicken** or **Guzman Bowl** meal and click
   **View glucose comparison**. Their notes identify `reference_semantic` and
   `reference_planned`. Skip the deliberately future-dated `future_meal` fixture.
   If already open, use **Find matches again**.
4. Use the notes to identify each fixture case. Names deliberately remain natural
   dish names so a `TEST` prefix does not distort semantic matching.

## Cases

| Notes identify this case | Full-serving carbs | Fraction eaten | Purpose |
| --- | ---: | ---: | --- |
| reference_planned | 55 g | Unknown | Main Guzman Bowl query; planned-serving basis |
| reference_semantic | 55 g | 1 | Chicken bowl query; consumed basis |
| exact_match | 55 g | 1 | Exact dish and amount |
| shared_portion | 110 g | 0.5 | Consumed amount is 55 g |
| similar_name | 58 g | 1 | Related chicken bowl name |
| partial_curve | 52 g | 1 | Eligible curve with an intentional gap |
| carbs_too_high | 100 g | 1 | Excluded by carbohydrate tolerance |
| different_dish | 55 g | 1 | Sushi; tests dish filtering |
| unknown_consumption | 55 g | Unknown | Excluded as historical evidence |
| not_eaten | 55 g | 0 | Excluded |
| unknown_carbs | Unknown | 1 | Excluded |
| missing_glucose | 55 g | 1 | No historical glucose window data available |
| conflicting_glucose | 55 g | 1 | Only flagged readings; excluded |
| future_meal | 55 g | 1 | Future records must not become historical matches |

The synthetic curves cover meal time ±2 hours at five-minute intervals. Their
shapes are invented mathematical examples, not physiological measurements or
predictions. The partial curve omits readings from +25 through +45 minutes.
The two reference windows overlap, so they share the same stored samples at
overlapping measurement times rather than inventing contradictory readings.

## Verified results

The applied fixture contains **14 meals and 536 unique synthetic readings**.
Authenticated calls to the actual matching endpoint returned:

- `reference_planned`: `exact_match` (55 g), `shared_portion` (55 g consumed),
  and `partial_curve` (52 g).
- `reference_semantic`: `similar_name` (58 g), `exact_match` (55 g), and
  `shared_portion` (55 g consumed). Cross-name cosine similarity was approximately
  0.925 with the configured embedding model.

All negative-control cases were excluded, repeated requests returned the same
meal IDs, and the demo token received 404 for another account's meal-comparison
and glucose endpoints. Verification used real embeddings, not fabricated vectors.

The fixture account has a **disabled, synthetic-only** connection without Dexcom
credentials. Its collection jobs are marked done. The live worker will not fetch
or overwrite fixture readings. New meals logged manually in this account will
not acquire real glucose readings unless you independently connect a real account;
doing so is unnecessary for this retrieval check.

## Rerun and verify

From `services/api`:

```sh
uv run python scripts/seed_retrieval_demo.py --verify
```

The script is restricted to loopback Supabase/database addresses. Fixture record
IDs are deterministic, and rerunning replaces only its own synthetic samples and
meals instead of duplicating them. It restores fixture quantities after manual
edits. The original fixture dates are retained between runs.

Verification invokes the actual FastAPI matching endpoint with the demo user's
real authenticated token, using real OpenAI dish-name embeddings. Embeddings are
cached by the ordinary retrieval service. Only synthetic dish names are supplied
to OpenAI. The script checks candidate exclusions, usable readings, repeated
results and rejection of another user's meal/glucose IDs. No credentials or tokens
are printed by the verification report.

The fixture is a local data seed, not a schema migration, so it will not be
automatically deployed with application migrations.

## Remove the fixture

```sh
uv run python scripts/seed_retrieval_demo.py --cleanup
```

Cleanup removes the dedicated fixture account, its meals, curves, queued jobs and
cached embeddings. It refuses if the account has additional non-fixture meals or
an enabled/non-fixture Dexcom connection. Your original accounts are unaffected.
The credentials manifest is replaced with a removal marker; remove that marker
file yourself if you later want to create a fresh fixture account.
